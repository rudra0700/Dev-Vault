## All about server

**`What is web server?`**

A web server is a program running on a computer. A web server is a combination of computer hardware and software that stores websites files. A web server delivers static files such as HTML, CSS, JavaScript, images, fonts, videos, PDFs, etc via `http` or `https`. Actually JavaScript is also static content.

Think of a web server as a waiter in a restaurant .

`The waiter:`

- receives your order
- finds the requested item
- gives it back to you

The waiter usually doesn't cook the food. Similarly, a web server usually:

- receives an HTTP request
- finds the requested file/resource
- sends it back

`Examples:`

- Nginx
- Apache
- Caddy
- IIS
- Node.js (when you create an HTTP server)

A web server's primary job is to hand over files/resources.

### **`Does a web server itself can produce html file, image and css directly or just it borrowed from somewhere else?`**

Depends what you mean.

**`Pure web server (Nginx)`** : Usually no. Nginx doesn't magically write HTML pages. It simply reads : 

```javascript
<h1>Hello World</h1>
```

from a file and sends it.

**`Application server (Node.js, Express)`** - Now things change.

This code block : 

```javascript
app.get("/", (req, res) => {
  res.send("<h1>Hello World</h1>");
});
```
Creates HTML on the fly. No HTML file exists. The server generates it dynamically.

Web server like Nginx and apace cant generate `html`, but express, django, next js, laraval can produce the html on the fly.

### **`Where do HTML, CSS, JS files live?`**

Usually on the hard drive (SSD/HDD) of the computer where the web server runs. A developer wrote them ahead of time and put them in a folder on the server's machine (or file system). The web server (like Nginx, Apache, or a Node.js server) just reads that file and sends its contents over HTTP when requested.

```javascript
website/
│
├── index.html
├── about.html
│
├── css/
│   └── style.css
│
├── js/
│   └── app.js
│
└── images/
    └── logo.png
```

Your web server knows **`"My website files are inside this folder."`**

For example Nginx may be configured like:

```javascript
root /var/www/website;
```

Now when someone requests:

```javascript
GET /
```

Nginx looks inside:

```javascript
/var/www/website/index.html
```
So it simply reads the file from disk into memory and sends it over the network.Strictly speaking, the web server mainly handles HTTP and forwards the request to the application.

So both can happen:

- static files → read from disk
- dynamic content → generated by application code

### `What does "static" mean?`

Static means:
Static = the file's content doesn't change based on who's asking or when. It's a fixed, pre-written file sitting on disk. Every visitor gets the exact same bytes.
The file already exists before the request arrives to the backend`(application server)`.

Example:

`index.html`

```javascript
<h1>Welcome</h1>
```

### `Why images, files, pdf, video are Static?`

Any file that does not change based on who is looking at it or when they are looking at it is considered **`static`**.

- **`Pre-made:`** These files are created beforehand (e.g., you take a photo, record a video, or save a document as a PDF) and saved to the server's hard drive.

- **`No processing needed:`** The web server does not have to run any code or talk to a database to generate them.

- **`Identical for everyone:`** If 100 people download the exact same link to a PDF, all 100 people get the exact same file


### **`Dynamic content`**

JavaScript runs (executes logic) once it reaches the browser — but the file itself , as it travels from server to browser, is just static text, delivered the same boring way as everything else. The server isn't "running" the JS; your browser is, after downloading it.

Suppose Facebook. When you open :

```javascript
facebook.com
```
You see your name, your posts , your notifications

`I see different data.` Because the page is generated based on the user. That's `dynamic content.`

You requested it today. You request it tomorrow. You request it next week. The content is identical. That's called `static`.

**`Question`**

suppose i host a node js application server in aws, what would be the step by step scenario?

To host a Node.js application server on AWS, you generally place a web server in front of your Node.js application server for security, speed, and reliability.

Here is the step-by-step scenario of how a user request flows through AWS to your servers.

The Infrastructure Setup
AWS EC2 Instance: A virtual cloud server where your software lives.

Nginx (Web Server): Installed on the EC2 instance to act as a Reverse Proxy. It faces the public internet, manages SSL certificates, and handles incoming HTTP requests.

Node.js (App Server): Runs on the same EC2 instance (usually on an internal port like 3000). It is kept safe behind Nginx and handles the database and business logic.

PM2 (Process Manager): Keeps your Node.js app running continuously in the background.

Step-by-Step Request Scenario
Step 1: The User Initiates

A user types your domain into their browser.

The request travels over the internet via HTTPS toward your AWS EC2 public IP address.

Step 2: The Web Server (Nginx) Intercepts

Nginx listens on public ports 80 (HTTP) and 443 (HTTPS).

It intercepts the user's request first.

Nginx quickly handles the SSL/TLS decryption to ensure the connection is secure.

If the user just asked for a static image or a CSS file, Nginx delivers it instantly without waking up Node.js.

Step 3: Nginx Hands Off to Node.js

If the request requires business logic (like logging in or fetching dashboard data), Nginx acts as a bridge.

It forwards (proxies) the request internally to http://localhost:3000, where your Node.js application server is listening.

Step 4: Node.js Executes Business Logic

Node.js receives the request from Nginx.

It executes your JavaScript backend code.

It talks to your database (like AWS RDS or MongoDB) to fetch or update data.

It constructs the final JSON data or HTML page.

Step 5: The Response Returns
Node.js sends the completed data back to `Nginx`.

Nginx receives it, packages it into a standard HTTP response, and sends it back to the user's browser.

 How it works: When you run a Python script, the Python software environment reads your code line-by-line, translates it into machine code on the fly, and passes it to the physical CPU.
 
 Backend Web Frameworks: Just like Node.js has Next.js, Python has frameworks like Django or FastAPI to build application servers.

 . C++ (The Compiler Setup)
 
 C++ works differently. It does not use a running software environment on the production server. Instead, it uses an environment during development to build a standalone file. It is a compiled language.
 
 The Software Environment: During development, you use a software environment called a Compiler (like GCC or Clang).
 
 How it works: The compiler takes your raw C++ code and translates the entire thing ahead of time into a raw, binary executable file (like a .exe on Windows or a binary file on Linux) made of pure 0s and 1s.
 
 On the Production Server: When you deploy C++ to a physical AWS server, you do not install a C++ environment. You just upload that binary executable file. The physical CPU reads it directly because it is already in the computer's native language.
 
 Backend Web Frameworks: Frameworks like Crow or Drogon allow C++ to act as an incredibly fast application server.

When you search for something on Google and get the results, Google's backend servers do not just send you raw JavaScript code for your browser to build from scratch. Instead, they send you fully assembled HTML code first, along with some JavaScript to handle the interactive parts.

Here is exactly how that final handoff works between Google's servers, your browser's V8 engine, and your physical CPU:

1. The Server Pre-Assembles the Page (HTML)

Google's backend application server (written in C++ or Java) does the heavy searching and ranking. It doesn't force your browser to do that work. The server creates a finished HTML blueprint of the results page. This HTML already contains the text of the links, titles, and descriptions.

2. What Your Browser Receives

Your browser receives a bundle from Google's web server containing:

HTML: The structured layout and text of the search results (so you see the page instantly).

CSS: The styling (fonts, colors, and layout rules).

JavaScript: The code for interactive features (like dropdown menus, tracking clicks, or auto-suggesting words if you type more).

3. Enter the V8 Engine and Your CPU

Once that bundle hits your laptop or phone:

The Browser's Rendering Engine reads the HTML and CSS to paint the visual boxes and text on your screen.

The V8 Engine (inside Chrome or Edge) wakes up specifically to handle the JavaScript part of that bundle.

V8 reads Google's frontend JavaScript code, instantly compiles it into machine language (0s and 1s), and feeds those instructions straight to your physical computer CPU.

Your CPU executes those instructions, which makes the page interactive (e.g., allowing you to filter results, open image previews, or infinite-scroll).
